# MedStart: архитектура устойчивой работы в России

## Неподвижное ядро продукта

MedStart — не Zoom и не LMS. Это единое рабочее пространство медицинского
репетитора и студента:

```text
репетитор → подтверждённое занятие → MedStart Live
                                  ├── видео и голос
                                  ├── совместная умная доска
                                  ├── демонстрация экрана
                                  └── чат и сохранённые материалы
```

Видео является частью занятия, а не отдельной внешней ссылкой. При ухудшении
сети приоритеты меняются в таком порядке:

1. сохранить голос;
2. сохранить синхронизацию доски;
3. сохранить чат;
4. уменьшить или отключить видео;
5. после восстановления сети автоматически дослать изменения.

## Что означает «устойчиво»

Абсолютная работа при полном отключении мобильного и фиксированного интернета
невозможна для любого веб-сервиса. Реальная инженерная цель MedStart:

- не зависеть от обязательного VPN;
- не зависеть от Zoom, Google Meet или зарубежного видеохостинга;
- иметь несколько транспортов WebRTC;
- продолжать занятие голосом и на доске, когда видео уже не проходит;
- сохранять локальные изменения при кратковременном обрыве;
- иметь минимум два независимых узла и понятное переключение при отказе.

## Целевая топология

### Контур приложения

- фронтенд и API — российский хостинг;
- статические файлы — российский CDN или собственный edge-кэш;
- авторитетный DNS — два независимых российских провайдера;
- PostgreSQL — основной узел и реплика;
- Redis — realtime-состояние, очереди и маршрутизация комнат;
- S3-совместимое хранилище — материалы и фотографии;
- никаких внешних runtime-шрифтов, CDN-скриптов и обязательных зарубежных API.

### Контур связи

- два LiveKit SFU-узла у разных провайдеров;
- первый узел ближе к основной аудитории;
- второй — резервный в другом дата-центре;
- Redis для распределённой маршрутизации;
- WSS через TCP 443;
- WebRTC UDP как основной быстрый транспорт;
- ICE/TCP как первый резерв;
- TURN/UDP на 443 как резерв для фильтрующих сетей;
- TURN/TLS на TCP 443 как последний realtime-резерв.

Одна конкретная комната остаётся на одном SFU-узле. Новый урок направляется на
доступный узел, а отказ узла обрабатывается переподключением клиента и
перевыпуском короткоживущего токена.

## Уровни деградации связи

| Режим                | Видео                    | Голос           | Доска             | Чат               |
| -------------------- | ------------------------ | --------------- | ----------------- | ----------------- |
| Нормальный           | 720p, несколько слоёв    | да              | realtime          | realtime          |
| Ограниченный         | низкий слой / меньше FPS | да              | realtime          | realtime          |
| Экономный            | выключено                | да              | realtime          | realtime          |
| Краткий обрыв        | выключено                | переподключение | локальная очередь | локальная очередь |
| После восстановления | по выбору                | автоматически   | досылка           | досылка           |

В клиенте уже включены adaptive stream, simulcast, dynacast, повторные попытки
соединения, предварительная проверка камеры/микрофона и ручной быстрый переход
на голос с доской. Живые штрихи доски разбиваются на пакеты меньше сетевого
MTU, а итоговый штрих повторно передаётся надёжными порциями и сохраняется
долговременно. Если видеоконтур отключён, интерфейс не имитирует звонок и
открывает отдельный режим доски без LiveKit.

## Скорость сайта

В текущем исходнике выполнено:

- клиентская навигация Next.js;
- предварительная загрузка ролевых разделов после входа;
- предварительная загрузка запускается только в простой браузера и отключается
  при `Save-Data`/2G, чтобы не конкурировать с первым экраном;
- мгновенные loading-состояния маршрутов;
- системный шрифт без runtime-запроса к Google Fonts;
- отдельный пакет видеокомнаты: LiveKit не грузится в каталоге, профиле и
  расписании;
- Firebase Storage вынесен из стартового пакета и загружается только там, где
  нужна фотография;
- кэширование статических файлов Service Worker;
- офлайн-экран без кэширования приватных страниц кабинета;
- постоянный локальный кэш Firestore для повторного открытия данных и очереди
  записей.
- расчёт занятий по сохранённому часовому поясу, а не по текущей зоне
  устройства.

Целевые метрики после переноса на production-хостинг:

- LCP главной и кабинета: до 2,5 с на обычном 4G;
- переход между уже загруженными разделами: визуальная реакция до 100 мс;
- API p95: до 300 мс внутри РФ;
- подключение к комнате p95: до 5 с;
- восстановление после смены Wi‑Fi/LTE: до 10 с;
- успешные подключения с TURN fallback: не ниже 99,5%.

## Важный переходный риск текущего MVP

Сейчас аккаунты, записи, чат и сохранение доски всё ещё используют Firebase, а
редактор проекта — Replit. Это подходит для закрытой проверки, но противоречит
жёсткому production-требованию «не зависеть от санкций и зарубежных платформ».

Перед публичным масштабированием обязательна миграция:

1. Firebase Auth → собственная серверная сессия/OTP;
2. Firestore → PostgreSQL + WebSocket;
3. Firebase Storage → российское S3;
4. Replit deployment → российский хостинг;
5. Firebase client SDK → внутренний API MedStart.

Новые модули видеокомнаты отделены так, чтобы LiveKit можно было развернуть
самостоятельно уже сейчас, а замену Firebase выполнить следующим этапом без
переписывания интерфейса занятия.

## Наблюдаемость и аварийный режим

- health checks сигналинга, TURN и API каждые 30 секунд;
- синтетический звонок между двумя тестовыми клиентами каждые 5 минут;
- метрики потери пакетов, RTT, jitter, reconnect и доли audio-only;
- тревога при росте неуспешных подключений;
- статусная страница на отдельном домене и провайдере;
- короткоживущие токены комнат;
- резервное копирование PostgreSQL и досок;
- запрет автоматической записи видео в первом релизе.

## Порядок внедрения

1. Подключить один self-hosted LiveKit + TURN/TLS в РФ.
2. Пройти сетевую матрицу двух операторов и UDP-blocked тест.
3. Добавить второй SFU-узел и Redis.
4. Перенести Next.js с Replit на российский хостинг.
5. Перенести данные и авторизацию с Firebase.
6. Провести нагрузочное тестирование и недельный пилот.

До завершения пунктов 4–5 нельзя рекламировать продукт как полностью
независимый от зарубежной инфраструктуры.
